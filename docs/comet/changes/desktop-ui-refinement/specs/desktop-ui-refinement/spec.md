# 桌面配置与操作反馈修复

## 1. 测试对象与事实
无修改时按钮为“测试”，测试点击时的当前有效配置（包括环境覆盖）；该服务商有尚未保存的实际变化时为“用未保存的修改测试”。空密钥保留原值，只有显式清除才测试空凭据。测试绝不自动保存配置。桌面测试沿用只读正式健康记录的行为；结果属于本次 App 会话，不伪称已保存配置获得持续健康保证。后台返回 current/draft 范围，状态包含测试时间。冷却记录和本次测试分开显示。

Web 适配器保留 None 与明确传入的空 overrides 字典的差别；不靠 `or None` 改变调用者表达的测试范围。CLI 不传 overrides 的既有正式探测行为不变。

### Scenario: A1 测试标签和健康记录与实际调用一致
在合成旧 Key、空修改、输入新 Key、擦除输入、显式清除和只改无关服务商的情况下，标签和实际请求配置相符；current/draft 结果范围准确。桌面两种测试都不修改配置文件或正式 provider_health 文件；Web 空字典不隐式转换为正式探测，未传 overrides 的既有行为保留。

## 2. 操作反馈与防重复
每个异步操作在第一次 await 前进入忙碌态，按钮显示进行中动作并禁止重复提交。服务商测试、业务运行、Skills 安装从请求受理一直保持到实际完成、失败、取消或失联；返回 run_id 不代表完成。不同服务商可独立工作，其他无冲突页面可操作。切页、状态刷新或控件重建不重置操作状态。断开、异常、超时、取消后恢复可用并解释结果。取消请求显示“正在取消”，直到后台终态。

### Scenario: A2 异步操作有即时反馈且不会重复发起
延迟模拟探针期间连续点击同一测试按钮只产生一次请求，控件和卡片显示测试中；切页返回仍忙碌。成功、timeout、失败、取消和断开后状态可恢复。保存/预览/运行/安装更新/手动刷新/更新检查/目录选择等操作由同一反馈规则覆盖，业务运行和 Skills 的忙碌持续至真实终态。

## 3. 原生视觉层次
沿用项目图标、系统字体和控件。使用明确的页面背景、内容卡片、轻描边、8–12px 圆角和 4px 间距倍数。标题、组标题、正文、次级说明分层；次级文本用主题语义前景色，不能靠统一 Opacity。主色只用于选择和主要操作；成功、提醒/超时、失败、进行中、中性状态同时有短文字和对应色。深色与高对比主题有可读前景/背景，图标容器不写死白色。

正文保持可读宽度并与内容左边缘对齐；宽窗不出现居中的悬浮窄带。活动项等宽。路径、配置键、掩码、时间和技术值使用等宽字体并允许换行；普通说明使用系统正文。窄窗表单列切为上下布局，无横向溢出或不可见操作。

### Scenario: A3 状态与主次信息在浅深色和不同宽度均可辨认
Windows 原生概览、服务商、搜索、活动、AI 接入、设置页面具备统一主次层次。通过、超时、失败、运行中、未测试/未安装不再同权重黑字；活动卡片等宽。常规窗、窄窗及最大化下无明显空白窄带或溢出；深色图标底、次级文字和状态文字可读，状态不只靠颜色。

## 4. 配置组织与渐进展开
根据后端 metadata 的 section/order、tier、provider、capabilities、placeholder/default、帮助和链接呈现。优先主搜索、文档检索、网页抓取，说明每类任选一个即可。基础项默认可见，服务商自己的高级项留在其分组内并默认折叠；其余服务商与路由/超时/诊断等高级区清楚区分，不按字母把诊断提前。68 项字段均可找到和编辑，没有重复绑定同一键的冲突控件。

有效值和来源在主视图明确，保存值与有效值相同不重复占两行；不同来源的保存值和技术键名可展开查看。提供已有 key_url/docs_url 的明确链接。预览/保存/未保存计数在长表单中始终可找到。

### Scenario: A4 基础配置先行且高级字段和来源信息不丢失
两端解析并消费 section order、tier、placeholder、default、capability_chains；首屏不以 diagnostics 开头。配置分组先显示三类基础能力，advanced 默认折叠，全部配置字段仍有唯一编辑入口；环境只读与有效/保存差异可见，默认值只做提示不被无意写回。长表单的保存操作保持可见。

## 5. 面向用户的中文文案
普通界面的命令/阶段/探针方式/错误类别采用中文动作或结论；closed/live/provider.test/version/regression/timeout 等技术值仅在需要的高级详情保留。状态先给“通过/超时/未配置/冷却中”等结论，再给短解释和时间。桌面命令描述不再直接显示 argparse 英文 help；CLI 自身的命令参数和 help 不受影响。

### Scenario: A5 常用界面没有未解释的内部状态码
测试超时、活动 provider.test/version/regression、Skills 缺失或过期、冷却状态和搜索工具描述均显示中文可理解文案；高级详情仍可取得原始信息，CLI 参数/输出约定保持不变。

## 6. 数据与交互连续性
修改中页面刷新、探针完成、切页回来不得清空配置输入或改变已选清除项。展开状态与滚动位置尽量保持。保存时防止重复写入并保留冲突草稿；密钥保留/清除和环境只读规则不改变。新运行不覆盖其他任务结果归属；仅取消 App 自有任务。无需用户配置时不发计费请求，测试使用本机合成数据。

### Scenario: A6 状态更新不破坏编辑与原有功能
输入尚未保存的值后等待另一服务商测试完成、刷新或切页，输入仍在；保存、冲突、空密钥保留、显式清除与环境只读回归通过。搜索结果/导出、活动取消和 CLI 独立运行保持原行为，真实用户配置和全局 CLI 不被测试改写。

## 7. 双端实现与验证边界
SwiftUI 端读取同一元数据，使用原生卡片/披露组/语义颜色和按动作记录的忙碌状态；补模型级检查覆盖 sections 排序、tier、默认/占位值、fallback chain 与操作生命周期。不能只修 Windows 后忽略已明确指出的 macOS 问题。当前没有 Mac 时记录未运行 build/test/GUI，并提供可在 Mac 执行的验证入口，沿用用户后续单独验收的决定。

### Scenario: A7 macOS 实现覆盖本轮要求且证据边界真实
源码与模型测试覆盖元数据解析/使用、基础项优先、advanced 折叠、测试范围、忙碌与重复提交保护、语义状态；独立审查没有明确遗漏。任何未执行的 Swift build/test 或原生界面验收均明确记为未验，不借 Windows 验收宣布 macOS 完成。

## 8. Windows 交付检查
使用当前修复源码构建独立 Windows x64 产物；以隔离配置和延迟/失败本机模拟服务实际检查。保存视觉与行为证据和准确源码/产物对应关系；保留原安装版本，待本轮另行明确要求后才覆盖安装或发布版本。轻量的样式/操作模型复用现有代码，不新增 UI 框架。

### Scenario: A8 修复结果可在本机验证并可追溯
相关 Python 回归、现有完整回归、Windows 构建与原生关键场景通过；构建输入对应最终修改。对照用户 Web 参考检查配置层次和忙碌反馈，并留实际窗口证据。源码、测试产物与未验范围明确，不把规划、静态检查或截图当作已发布安装。

## 9. 版本与更新入口（追加 Shape 草案，未获实现确认）

设置页集中展示两个更新对象：App（附内置引擎版本）和独立 CLI。App 与内置引擎一同分发、下载和安装；外部 CLI 版本、实际生效路径、安装来源与最新稳定版分别展示。GUI 与内置引擎版本不一致时明确报告，不用一个版本掩盖不一致。CLI 只指向 App 内置入口时标记“随 App 更新”，不重复当作独立安装。

CLI 状态刷新必须重新解析命令路径与版本，覆盖 App 运行期间 CLI 已由外部终端升级的情况。只读识别不得执行会自动安装/修复运行时的 wrapper，不调用搜索服务商或暴露配置凭据。发现其他安装副本可提示，不改 PATH 或替用户选择新的默认 CLI。

### Scenario: A9 App 和独立 CLI 的版本与来源准确
模拟 App 0.1.19、独立 CLI 0.1.20，界面分别显示，不能声称 App 也已更新；模拟 CLI 指向 App 内置路径时合并为随 App 更新。外部升级后点刷新，显示重新解析的路径与版本；普通 npm、mise shim、未知来源和多副本按可确认事实分类。探测不触发安装或修复。

## 10. 自动检查及版本选择（追加 Shape 草案）

推荐默认 App 启动后非阻塞检查，运行期间距上次尝试至少 24 小时才再次自动检查；设置可关闭，手动检查立即执行。同一更新对象的并发检查合并，首次 await 前显示检查中；自动检查不强制弹窗打断工作。保留上次成功结果、来源和检查时间，离线、超时、限流与无新版分开显示。关闭 App 后无需驻留服务或系统定时任务。

默认只用稳定渠道。App 根据 GitHub 官方 Release 的真实附件选择系统/架构匹配且完整可验证的最新稳定版本；CLI 独立使用 npm latest 与对应管理器的有效版本约束。使用语义版本比较，远端更旧不提示升级，未知/开发版本不假定可降级。新的 npm tag 或没有桌面包的 Release 不能独自触发“App 可更新”。

### Scenario: A10 自动检查和新版本判断正确
在相同、较新、较旧、v 前缀、预发行、开发版本、缺少目标架构附件、离线和 403/429 的合成响应中，状态与可执行动作准确。重复启动/手动连点不并发发出相同检查，手动操作有忙碌反馈；自动检查失败不把旧缓存冒充本次成功，也不影响搜索工作。

## 11. 安装包下载及发布契约（追加 Shape 草案，Q1 已确认）

自动查到新版后仅提示，用户点击“下载”才发起安装包下载；安装始终另经用户明确动作。每次下载绑定已选定的版本、平台、架构、资产标识、大小与 SHA256，不能下载到一半跟随变化的 latest。只接受固定官方仓库的可信 HTTPS 元数据及受控下载跳转，禁止从任意外部 URL 执行包；不把凭据附带给发布服务。优先使用已有 httpx 和 hashlib。

显示真实已下载字节/总大小与进度，支持取消、失败重试和同包去重；先写应用更新缓存的临时文件，通过大小与哈希校验后原子改名。校验失败、缺少校验信息、缺包或错架构时不提供安装动作。哈希只能证明与发布记录一致，不声称等同系统代码签名；未签名包在下载/安装入口明确标识。完整缓存可复用，重试可以重新下载，不要求差分、断点续传或后台服务。

发布流程需为可交付的目标平台上传安装包及校验信息；以各平台资产就绪为准，不把短期 Actions artifact 当作正式更新来源。只有 Windows x64 包的发布对其他平台显示包未就绪；允许显示较新的 npm CLI，同时 App 留在上一可安装版本。

### Scenario: A11 下载状态和完整性可验证
使用本机合成服务覆盖正常下载、重复点击、取消、网络中断、错误大小/哈希及错架构；仅正确完整的包进入“已下载”并可打开。未完成或错误临时文件不能执行，旧已安装版本保持不变。正式发布清单和客户端选择规则在相同输入下得到一致目标，不误用 CI 临时产物。

## 12. 安装和 CLI 更新边界（追加 Shape 草案，Q2 已确认）

第一版建议沿用现有安装器：Windows 在用户点击后启动当前用户 Inno Setup 包；退出 App 前先处理未保存配置和 App 自有任务，有未处理内容时允许返回，不强制终止或覆盖运行中的后端。macOS 提供打开已校验 DMG 的系统入口及正常安装提示，不自行覆盖正在运行的 .app。保留打开下载目录与版本说明入口；安装器已启动不等于安装成功，只有重新启动后的实际版本验证才报告完成。原配置和活动数据不随应用更新删除。

CLI 已确认识别为普通 npm 全局安装或 mise npm 管理的独立 CLI 时，由 App 展示路径、原版本、已解析的目标稳定版本和将执行的作用范围，用户点击“更新 CLI”后调用原管理器更新。使用确切已发现的管理器及参数，不执行从远端元数据拼成的脚本；不运行全局批量升级，不切换管理器或覆盖锁定的项目环境。更新完成重新解析路径和版本验证；失败如实展示，不能只凭进程退出即称成功。包管理器执行中不能承诺任意强制取消后安全回滚；保留可读日志且不泄露密钥。

同时保留可复制的单工具更新命令，允许用户自行执行后在 App 刷新验证。未知来源、项目 venv/开发检出、多来源无法确认、当前环境版本约束冲突均给出可操作说明，不猜测或强改。App 更新不终止外部 CLI 任务；CLI 更新必须处理已知占用或管理器失败，不能杀掉终端/AI 进程。

### Scenario: A12 更新只作用于所选对象且结果真实
在隔离 App 安装目录与管理器测试替身中验证：App 操作不改独立 CLI/PATH/配置；有草稿或 App 自有任务时不强制退出；未知 CLI 来源不代执行；npm/mise 命令只针对 Smart Search，版本读回不符时不报告成功。下载完成、安装器启动、安装成功分别显示。macOS 尚未执行的系统安装验证明确留作未验。

## 13. 社区贡献的工具链和 Markdown 输出

保留 PR #38/#42 的源码和提交归属，mise 为可选开发入口，固定 Python/Node 版本、调用项目自己的虚拟环境。通用 CLI/Python 入口正确传递参数，check 覆盖 src/tests；不改变用户 npm 分发方式或全局默认工具。Markdown 的路径、URL、配置标识值保留完整字符串和转义，普通说明文字可保持长度上限。

### Scenario: A13 mise 与长标识符在 Windows 可用
在隔离检出验证 mise 的解释器/模块路径、参数转发、源码测试和检查任务；构造超过 160 字符的路径、URL 和配置地址，实际 Markdown 输出保留完整值与竖线转义，普通说明仍可截短。安装运行时下载失败与代码失败分开记录。

## 14. Tinyfish 的双能力和桌面接入

按 PR #40 提供 search/fetch 共享 Key 的可选渠道，使用官方各自端点及 X-API-Key。保留原兜底顺序、来源格式、端点变化解除旧指纹冷却的语义。共享健康记录的成功探测必须覆盖实际声明的能力，不用搜索成功宣称抓取端点也成功。识别每 URL 错误和挑战页，遵循超时预算并脱敏错误。新增字段可从原生 App/Web 配置，写入时校验，Tinyfish 卡片可测试未保存值且不写正式健康记录。

### Scenario: A14 Tinyfish 搜索抓取与配置状态真实
模拟和受控真实请求分别覆盖搜索和抓取；Desktop/Web 的新增四字段、类型、掩码与草稿探针可用。错误 fetch 地址不会因 search 成功被误报为全部正常；HTTP/逐 URL timeout、bot_blocked、404 和合成 Key 回显得到正确分类/脱敏，配置修改后恢复规则可验证。

## 15. JEV 为可选推荐的语义路由

保留 hybrid/rules/off 及未启用 JEV 的原行为。JEV 只在用户选择后参与联网，使用独立 TypeSafe 配置；推荐文案不等于静默切换。配置、诊断、CLI、原生 App/Web 均展示完整字段及范围。

候选集合由程序根据配置、能力、允许列表、禁用、冷却及 explicit-only 限制构成，JEV 只对已有候选给出判断，不能新增任意执行器或 URL。把服务商专长和已有用户偏好提供给判断，Exa 的新闻/官方来源、Grok 通用检索、Context7 库文档作为可用专长；不把偏好变成跨能力强制替代，也不把概率称为人工权重。优先复用已存在的 preferred providers 配置，避免另造一套分数公式。route/deep 的本地诊断和离线规划边界明确；需要远程判断的入口必须显式表达，不能号称免费本地预览却计费。

### Scenario: A15 可选路由、偏好和入口边界一致
未启用 JEV 时既有搜索模式回归保持；启用后候选排除未配置、禁用、硬冷却及显式限制渠道。改变已存在的 provider preference 会体现在判断输入及可解释结果；未授权网络的 route/deep 不调用 TypeSafe。桌面可配置 JEV 且密钥不会进入候选、错误或活动日志。

## 16. 基于证据的连续检索决策

日常 JEV 搜索先选操作，执行后判断累计证据的相关性、可用性、充分性和缺口；结果不足时可以切换引擎、选择缺口相关的新检索词或抓取已发现的 URL。同一引擎允许不同查询，完全相同的 provider/操作/查询/URL 不重复执行。候选查询先复用原问题、已有研究计划的子问题及明确的缺口检索词；JEV 是判断器，不假装具有自由文本生成接口。

默认有限轮数、每轮渠道数、结果数和共享截止时间；每次 await 后和派发前检查预算，取消及时停止子任务。达到足够、没有新动作、轮数/时间耗尽或持续没有新证据时停止，保留部分证据和真实原因。过滤可选，只删明确无关内容、失败保留；内容改变后重新核验充分性。汇总 true/false/auto 沿用 PR 语义，依据最终保留证据判断，失败返回证据。

### Scenario: A16 日常检索能判断不足并选择有效后续动作
合成场景覆盖：首轮不相关后换引擎、首轮部分答案后同引擎新 query 补缺口、发现 URL 后抓取、没有新增证据时停止；记录每步查询/渠道/原因/判断/耗时与真实用量。相同动作不重复；总预算耗尽后不派发新请求；过滤删除关键证据后不能继续声称 sufficient。

## 17. JEV 参与完整 Deep Research

research 保留既有计划、预算等级、子问题、证据归档和结果字段，以 JEV 选择下一组检索/阅读动作并持续检查缺口。quick/standard/deep 的资源范围必须可观察地不同，配置允许扩展，但每次运行仍然有界。deep 命令继续是离线计划器。

搜索摘要和模型回答只作为发现候选，research citations 必须来自实际 fetched/read 文本；Context7 实际文档属于 read，库介绍不属于。真实正文失败、来源不够或存在未解决缺口时明确降级，不通过 JEV 的“足够”概率绕过事实约束。证据目录默认/显式行为、report/evidence/plan 和 final_answer/citations/evidence_items/gap_check 等契约保留。

### Scenario: A17 研究组合自主而证据契约不退化
对多子问题场景，JEV 可跨轮组合配置好的新闻、通用、文档和抓取能力；至少覆盖两种操作及实际阅读。只有摘要、抓取失败或只剩模型回答时不能冒充可靠引用；三种预算和取消均有界，报告字段与证据文件可追溯，旧 research 模式仍通过原测试。

## 18. JEV 失败降级与判断预算

JEV 缺失/无效/超时/限流、无法选择或判断不可用时，按已配置且允许的能力使用确定性候选兜底，并明确标记原因、来源和无法验证的部分，不调用旧 embedding/classifier 伪装 JEV 成功。fallback=off 继续尊重用户禁止补搜的选择。没有可用渠道时明确失败。

模型输入使用有总量上限的证据预览并如实记录截断/省略，不用无限列表或最小片段长度突破预算。概率响应验证类型、有限值及范围；只消费本次已发问题 ID。JEV 判断和汇总成本独立记录，不保证一定节省总 token。

### Scenario: A18 故障仍有可解释、有预算的降级
覆盖无 Key、鉴权失败、429/529、超时、无候选、无合适选择、非法概率和未知 ID。可用能力按规则执行且禁用/过滤/冷却仍有效；输出清楚说明降级。大量长证据不突破预览总量，取消和截止时间后无新调用，日志不泄露任何真实或合成密钥。
