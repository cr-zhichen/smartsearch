# Windows 自签名发布

## 目标与边界

Windows x64 与 ARM64 使用持续复用的 Smart Search 自签名代码签名身份，为项目自己的 Windows 程序、安装器与卸载器提供 Authenticode 文件完整性和身份匹配检查。自签名不是公开 CA 信任，不能以签名成功推断普通 Windows 电脑已信任发布者或 SmartScreen 不再提示。macOS 签名与公证不属于本能力。

复用现有 PowerShell、GitHub Actions、PyInstaller、dotnet 和 Inno Setup 发布流程。正式发行物签名失败即停止；PR/普通测试构建无需持有发布私钥并保持 unsigned-test 明确标识。

## 身份与秘密

创建一个 Windows 专用 RSA/SHA-256 代码签名证书，主题为 Smart Search，含代码签名用途并有明确到期日。x64/ARM64 和后续版本复用它。公开 CER 与 SHA-256 指纹、用途和到期时间可随源码分发；加密 PFX、密码及其 Base64 内容不进入源码、日志、聊天或 artifact。

本地备份仅保存到仓库外的当前用户私有目录并限制访问。CI 的 PFX 与密码通过 konbakuyomu/smartsearch 仓库的独立 GitHub Actions Secrets 提供。导入时核对期望证书、代码签名用途、有效期和私钥可用性；不得仅凭一个同名证书选取身份。发布构建不生成新身份，不导出他人证书或秘密。

### Scenario: A1 持续身份与秘密隔离

首次准备产生可复用的 Windows 签名身份，公开证书确认没有私钥，PFX 受随机密码保护并置于仓库外的受限目录；仓库只出现公开证书和其公开元数据。GitHub Secrets 的设置只打印名称/操作状态。后续构建核对并复用该身份；证书指纹不匹配、用途错误、到期、缺少私钥或密码错误均不能用于发布。

## 签名范围与顺序

完成编译及产品/版本资源后，对 SmartSearch.Desktop.exe、SmartSearch.Desktop.dll 和 backend/smart-search.exe 签名；复制、压缩和打包后不修改这些文件内容。依赖提供方的库保留原内容和已有签名，不批量以 Smart Search 重签。

Inno Setup 同时覆盖最终 Setup 和部署的卸载器，不能仅在未签名内层程序的安装包外添加签名。所有自有签名都使用 SHA-256 与可验证的时间戳。输出记录应明确证书指纹、文件摘要、时间戳、签名检查和系统信任结果；不能把只有哈希或证书对象存在当成验签。

### Scenario: A2 Windows 发布物完整签名

为 x64 和 ARM64 生成签名发布物后，App EXE/DLL、冻结后端、安装器及其实际携带的卸载器均带期望证书的 Authenticode 签名和时间戳，且内容完整性检查通过。产品名称和版本资源与构建版本一致。第三方库的签名前后摘要相同。证据必须区分本机实际构建、CI 实际构建、静态审查和未运行项目，不能以一种架构代替另一种架构。

## 验证与失败行为

签名和验签流程使用固定公开证书作为期望身份。明确区分内容完整性、身份匹配、时间戳和系统信任，不把任意 NotTrusted/UnknownError 一律当成成功。正式签名失败不得回退到未签名正式包。

本机及安装后的用户系统不自动导入受信根、不关闭 SmartScreen、不改变机器安全策略。CI 若需要信任导入，仅在可丢弃 runner 上对已核对的公开证书临时使用，并记录其范围；这不能作为终端用户已信任的证据。

### Scenario: A3 异常和不受信任状态不会冒充成功

可运行检查覆盖：缺失签名秘密、错误密码、错误证书、内容被篡改、缺失时间戳、签名工具失败。对应发布操作失败并阻止上传；秘密不出现在错误信息中。正确自签名文件在未导入信任的环境仍明确报告不受系统默认信任，不能将其写成公开可信。构建与验收不永久修改本机信任库。

## CI 与现有更新兼容

只有受信维护者发起的受控构建能使用签名 Secrets；来自 PR 的任意代码不能获得私钥，不能通过 pull_request_target 执行 PR 工作树配合发布秘密。签名输出通过核验后才能作为发布候选或上传已有 Release；签名失败时停止依赖的发布动作。

Windows 正式安装器使用 SmartSearch-{version}-win-{architecture}-Setup-signed.exe；文档明确 signed 在本项目为 self-signed。旧 unsigned-test/unsigned 资产保持可读，同一个平台/架构必须只有一个可选安装器。保留版本匹配、平台匹配、SHA256SUMS 完整性校验和既有下载来源限制。macOS 产物行为保持原有边界。

### Scenario: A4 流水线失败阻断且更新器能识别签名资产

现有 release 文件名校验接受两种 Windows signed 安装器，并继续校验现有 macOS 资产与版本。App 的资产选择能识别新 Windows 文件、拒绝平台不符或冲突资产，并继续读取历史未签名资产。PR 测试不访问发布 Secrets。至少以真实 Windows 签名构建和可运行的发布/资产检查验证；只有实际成功运行 GitHub Actions 后，才报告线上 CI 已通过。

## 用户文档与交付

提供公开证书获取位置、指纹核对方式和 Windows 首次运行说明。将“更多信息/仍要运行”描述为系统允许时的一次运行选择，而不是永久信任证书；不承诺每个下载或每台机器只提示一次，不要求用户关闭保护或自动导入根证书。若系统策略不允许继续运行，如实说明限制。

### Scenario: A5 说明与证据保持一致

中英文下载/发布文档明确自签名、Windows 默认不信任、可能出现的首次运行提示、官方来源和证书指纹；不出现已获得 CA/SignPath 信任或 macOS 已签名等错误声明。报告列出实际验签文件、测试结果、CI 状态以及 GUI/干净机器/ARM64 实机等未运行边界。生成候选产物不自动发布新版本、覆盖旧发行附件或替换本机正式 App。
