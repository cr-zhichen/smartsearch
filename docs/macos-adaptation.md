# macOS 适配阶段记录

分支：`codex/macos-native-adaptation`。上游：`konbakuyomu/smartsearch`；阶段提交推送至 `cr-zhichen/smartsearch`，全部适配完成且维护者验收后才向上游创建 PR。

## 分阶段交付

0. **安装基础**：保存已验证的 DMG 签名、安装布局、成品检查和 `.DS_Store` 忽略规则。
1. **启动与系统集成**：复现并修复 Swift 客户端启动超时，修复 Dock 和菜单栏图标，确认真实应用启动与关闭/重新打开路径。
2. **原生界面**：以 UTM 中正在运行的 Windows 版为功能依据，参考 DJOneHub / Codex Tweaks 的 macOS 原生层级；逐页调整导航、概览、服务商、搜索、活动、Skills 和设置。
3. **验收**：构建可安装产物并交给用户检查语言、主题和窗口尺寸。按照用户最新要求，不再自动操作主机或虚拟机、不再替换已安装的 App；实际界面与交互由用户验收。获准后再创建上游 PR。

每个阶段都单独提交并推送。不会把进程存在、后端单独 smoke 或编译成功等同于完整 App 验收。

## 设计方向

- 保留 Windows 已有功能和工作流，使用 macOS 的原生 `NavigationSplitView`、选择态列表、工具栏和系统语义色。按用户后续指定，以 Codex Tweaks 的页面布局为主要参照；不再把复杂工作页整体放入分组 Form。
- 使用 SwiftUI Scene 管理主窗口，保留当前 SDK 的原生系统材质；兼容原有 macOS 13 最低版本，不用自建 AppKit 窗口取代原生层级。
- Dock 使用应用品牌图标，菜单栏使用紧凑模板符号；不把大尺寸彩色应用图标直接用于菜单栏。
- 状态表达有实际依据：启动、连接失败、重试和就绪清楚区分，不隐藏错误、不通过延长超时掩盖通信问题。
- 不编写 UI 单元测试；以实际构建、协议进程集成检查和原生窗口验收为依据。

## 阶段 1

- Release 模式直接编译原有 Swift 通信客户端，连接实际安装的 Python 后端；12 次冷启动中 4 次出现握手超时。后端单独启动约 0.2 秒，不能靠增加超时解决。
- 旧实现为每个 stdout 数据块新建一个 `Task`，不保证数据块抵达 actor 的顺序。改用 `AsyncStream` 和一个消费者，按管道顺序组装 JSON；同时在退出时完成流并取消读取任务，取消的超时任务不再继续执行。
- 修改后同样 12 次握手全部成功。新增 `mise run desktop:macos:backend-check /path/to/backend`，以 Release 优化编译生产客户端，检查 12 次启动/停止/重连，每次还发送 4 个并发完整状态请求和 ping；全部通过。使用隔离配置，不调用付费搜索。这是实际进程集成检查，不是 UI 单元测试。
- Dock 从应用包显式读取品牌图标；菜单栏使用系统 `magnifyingglass` 模板符号，避免彩色应用图像的固有尺寸撑开菜单栏。
- 主窗口保持 SwiftUI Scene 管理，改为单窗口并设定默认尺寸；侧边栏采用原生选择态，连接状态移至底部；窗口关闭后隐藏，菜单栏和 Dock 恢复同一窗口；增加 ⌘, 设置快捷键。
- 启动页显示真实进度，连接过程中不提供重复启动按钮。系统日志只记录握手完成耗时与失败状态，不输出响应内容或凭据。
- 用户已在本机确认第一阶段新构建正常。当前 UI 自动化工具读取此 App 窗口会断开，因此自动化截图和关闭/重开完整交互仍需后续验收；不据进程存在代替这些检查。

旧安装副本保存在本地 `.desktop-artifacts/adaptation/installed-before-stage1.app`。

## 阶段 2A：主要页面层级

- 概览、服务商、搜索与设置使用原生分组 `Form` / `Section`，标题由窗口工具栏统一承载，移除内容区重复大标题。使用系统字体和语义色，保留 SwiftUI Scene 窗口管理。
- 概览参照 Windows 的功能层级，先显示基础配置状态和下一步按钮，再显示能力状态；配置路径、协议信息和路由链折叠收起。未知状态仍明确显示未知，不视为已配置。
- 服务商按三类基础能力分组，每个服务商独立展开，初次显示时展开已有密钥配置的服务商；折叠标题仍显示未保存修改。保存、预览、放弃修改、手动测试和清除密钥的原有行为保留。
- 搜索保留后端工具目录、实验性标注和高级参数；文本参数有常驻字段标签，并可随多行内容扩展。结果复制、导出和来源链接继续保留。

- 新增 `mise run desktop:macos:compile`，只编译，不启动界面。新增文案同步至共享语言资源和 SwiftPM 资源。
- 活动与 Skills 页的专门布局调整留待下一小阶段；本次不宣称全部 macOS 适配完成。

### 阶段 2B 反馈：右侧统一背景

用户再次指出顶部侧边栏交界处色块突兀，并要求右侧全部具有白色背景。右侧页面原来使用灰色 `windowBackgroundColor`，卡片使用白色 `controlBackgroundColor`，工具栏又是另一层系统材质。

统一详情容器、滚动页、卡片、工具栏和服务商底部操作区的背景，使用 `textBackgroundColor`（浅色外观为白色，深色外观仍采用系统匹配背景）。详情背景覆盖顶部安全区，工具栏明确使用同一不透明背景，减少标题栏/内容区交界处的色差；内容本身仍遵守安全区。各页的宽度、内容组织和操作行为保留。实际顶部衔接仍需用户截图验收。

用户补充要求将复选框换成开关：在主界面统一使用系统 `.switch` Toggle 样式，覆盖 Agent 选择、Skills/App 自动检查、搜索布尔参数和活动记录选项。Agent 行改为左侧名称/状态、右侧开关，保留无障碍名称、原选择绑定与更新期间禁用状态；开启只表示选中目标，不会自动安装或更新 Skills。

## 阶段 2C：修正 linked-on SDK，恢复新系统原生外观

用户提供了 Codex Tweaks 与 Smart Search 的同屏对比，指出顶部、按钮和开关明显使用不同代际的外观。此前仅调整工具栏样式没有解决核心问题。

直接读取两份可执行文件的 `LC_BUILD_VERSION`：

| 实际二进制 | 最低运行版本 | linked-on SDK |
| --- | --- | --- |
| `/Applications/Codex Tweaks.app` 的两种架构 | 13.0 | 26.5 |
| 上一阶段 Smart Search 打包产物 | 13.0 | **13.0** |
| 本阶段重新链接的 Smart Search | 13.0 | **27.0** |

本机选中的 Xcode SDK 是 27.0，旧 SwiftPM 构建日志也指定了这个 SDK，但最终 Mach-O 错把最低运行版本记成 SDK。系统会依据 linked-on SDK 决定兼容行为；苹果说明新版外观需要用新版 SDK 重建，单纯使用 SwiftUI 并不足够。参见 [Platforms State of the Union](https://developer.apple.com/videos/play/wwdc2025/102/) 和 [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)。

- 新增 `compile-macos.sh`，从选中的 Xcode 读取实际 SDK 路径和版本，同时用于编译与链接的 `-platform_version`；不修改成品二进制，不伪造 SDK 版本，也不提高最低运行版本。
- 本地 compile 和正式打包共用此入口；低于 SDK 26 时清楚报错。历史 tag 构建时一起加载该脚本。
- DMG 校验新增真实 Mach-O SDK 检查：SDK 至少为 26、与构建工具链一致，最低版本与 Info.plist 一致。已使用上一阶段真实旧产物验证检查会拒绝 SDK 13；新产物 SDK 27/最低系统 13 检查通过。这是产物元数据校验，不是 UI 单元测试。
- 移除强制不透明工具栏背景、覆盖顶部安全区的白底及冗余窗口工具栏样式声明，恢复与 Codex Tweaks 相同的系统窗口管理。仅内容区保留用户要求的白底，开关仍为原生 `.switch`。
- 没有加入自绘阴影或模拟玻璃；按钮、开关、侧边栏和工具栏交由系统按真实 SDK 绘制。实际外观依旧由用户验收，不操作桌面或虚拟机。
